The Edge-First Frontend: Standardizing Web Architecture on Cloudflare

By Anas Semesmieh · February 19, 2026

Cloud Architecture Platform Engineering Security

Frontend delivery was carrying the cost and operational shape of a backend platform, and the fix I proposed wasn't just an argument for "edge is good." I built the case to standardize Cloudflare as the default hosting and execution environment for all future UI/UX and presentation-layer workloads, backed by a proof of concept covering a static asset shell, SPA containers, and a headless CMS migration.

My design principle is explicit: serve at the edge, process and persist in Azure. Frontend delivery moves to Cloudflare, while transactional backends and sensitive data stay in Azure.

That distinction matters because this solves a concrete architecture problem. Frontend applications were running as Dockerized workloads on AKS, which meant Dockerfiles, Helm charts, cluster operations, region-bound latency, pre-provisioned compute, and maintenance overhead for systems that were primarily serving UI assets and presentation logic. That's the wrong operating model for the workload.

1. A detailed current-state versus future-state model

The current state was a centralized Azure-region deployment. Frontend workloads are containerized, tied to AKS, and paid for as provisioned capacity. That means costs remain high even when the system is quiet, and user experience is shaped by physical distance to a single primary region. There's deeper developer friction too: every frontend team effectively needs to understand container packaging and Kubernetes delivery just to ship presentation changes.

The future state is Cloudflare Edge: decentralized execution across Cloudflare's global network, event-driven scaling instead of provisioned nodes, GitHub-integrated deployment ergonomics, built-in OpenTelemetry export, and zero-downtime global updates. That's a direct architecture comparison across these dimensions:

  • Centralized AKS versus distributed edge execution.
  • Provisioned scaling with lag versus elastic per-request scaling.
  • Docker, Helm, and deep Kubernetes knowledge versus code-focused frontend delivery.
  • Node-based observability agents versus native telemetry export.
  • Maintenance windows and rolling restarts versus atomic, globally propagated updates.

That's the first concrete problem this solves: frontend delivery was carrying the cost and operational shape of a backend platform.

2. The target architecture is layered and deliberately split across Cloudflare and Azure

The real effort shows in the technical architecture. Traffic enters through the nearest Cloudflare PoP. Before it reaches application logic, it passes through Cloudflare security controls including WAF, DDoS mitigation, and bot management. That makes the edge the actual front door rather than just a CDN bolt-on.

At the edge, I place presentation and content workloads on specific Cloudflare services:

  • A headless CMS hosted on Cloudflare Workers using D1 for edge-side content data and R2 for media assets.
  • Angular SPA assets served directly from R2 instead of from a containerized web server.
  • Dynamic image delivery handled through Cloudflare Images and R2.

The secure connectivity piece is just as important. Rather than exposing Azure services directly, I use Cloudflare Tunnel to create a private encrypted connection from the edge into Azure. Authenticated API requests route into Azure API Management, which fans out to the backend mix that stays in Azure: AKS-hosted microservices where still needed, Function Apps for event-driven logic, Logic Apps for orchestration, Azure OpenAI for AI-backed capabilities, and region-bound data services like SQL, MongoDB, Search, or Cosmos DB.

That's the second concrete problem being solved: the frontend platform needed a clean separation between internet-scale delivery and transaction-heavy backend processing instead of forcing both into the same hosting model.

3. Security, data residency, and observability as first-class design constraints

This is not a blanket migration of all systems to Cloudflare. I separate data classes and trust boundaries:

  • Public content and presentation-layer data can live at the edge in D1 and R2.
  • Sensitive and transactional data stays in Azure-region data stores.
  • Azure no longer exposes public ingress directly; traffic is forced through the Cloudflare edge and Cloudflare Tunnel path.

The observability piece deserves its own attention. I rely on native OpenTelemetry support at the edge and unified ingestion into Dynatrace for both Cloudflare Workers and Azure backend services. This isn't only about performance and cost — it's also about preserving end-to-end transaction visibility across a split architecture. The official OpenTelemetry documentation is relevant here because I'm standardizing around portable telemetry rather than environment-specific instrumentation only.

That's the third concrete problem being solved: how to gain edge performance and security controls without compromising regional data control or operational visibility.

4. The architecture choice is justified by burst traffic, latency, and operating cost

Two business-pressure arguments are also technical arguments. First, burst traffic during peak moments, where provisioned capacity and traditional autoscaling create either idle cost or reaction lag. I lean on Cloudflare Workers' isolate model and per-request scaling for elastic handling of sudden spikes.

Second, global reach. Serving a geographically distributed user base from a single Azure region turns physical distance into a frontend performance problem. Cloudflare's Anycast network and large PoP footprint localize UI latency without replicating frontend clusters region by region.

The cost side adds the harder-edged operational claim: decommissioning two of three AKS clusters, with an estimated 65 percent compute reduction and corresponding drops in monitoring and security-tool surface area. This isn't an aesthetic migration — it's a platform simplification program tied directly to cluster reduction, licensing impact, and less Kubernetes maintenance work.

5. The implementation plan is what makes this credible

I avoid the usual architecture-slide failure by defining a three-phase roadmap:

  • Phase 1: Foundation, enablement, and governance. Continue the in-flight CMS-to-Workers and Cloudflare Images work, publish a developer guide, run workshops, and define strict scope boundaries so the pattern applies only to UI/UX and presentation-layer concerns.
  • Phase 2: Static asset migration. Move production SPA asset libraries to R2 and update GitHub Actions pipelines to publish artifacts directly to the edge.
  • Phase 3: Cutover and decommissioning. Route primary traffic via Cloudflare, drain frontend nodes from existing AKS clusters, and execute the cluster decommissioning plan.

That roadmap matters because the standardization effort wasn't just technical design — it included education, pipeline changes, scope governance, and staged decommissioning.

Closing thought

The technical insight here isn't just that Cloudflare can host a frontend. It's that presentation workloads, asset delivery, and edge-side content belong on a different operating model than the backend systems they talk to. I earned that conclusion with a concrete architecture, a staged migration path, and a security model that still keeps Azure as the system of record.
